Đánh giá kiến trúc src/

14 folder phẳng ở src/ trộn lẫn module nghiệp vụ (auth, staff, categories, products, product-options) với hạ tầng (prisma, mail, metrics, health, audit, bootstrap, cli, common, config). Trong khi đó docs/architecture/02-modules.md §4 đã có sẵn cây đích modules/ + infrastructure/, chỉ là chưa chuyển sang. Báo cáo này đề xuất cách chuyển sao cho mỗi module sâu hơn, không chỉ là đổi chỗ file.

1. Gộp Danh mục / Sản phẩm / Size-Màu thành module catalog

Strong

Files: src/categories/*, src/products/*, src/product-options/*, app.module.ts

Problem: Docs định nghĩa một module catalog sở hữu categories, products, sizes, colors, product_variants, product_images. Code tách thành 3 Nest module nông, mỗi cái tự import AuthModule, tự khai controller storefront + admin. Biến thể (Variant) phụ thuộc Size/Màu nhưng Size/Màu nằm module khác → products/dto/option-summary.dto.ts phải tự định nghĩa lại hình dạng của Size/Màu. Hiểu "một Sản phẩm được bán thế nào" phải nhảy qua 3 folder. Khi làm pricing, cart, inventory (đều --> catalog theo sơ đồ phụ thuộc) sẽ phải chọn import từ 3 chỗ.

Solution: modules/catalog/ với một catalog.module.ts, chia storefront/ và back-office/ (đúng mẫu ở 02-modules §4), service theo use case (category-tree, product-lifecycle, variant, option). Module chỉ exports một interface đọc nhỏ cho module khác (vd. tra Biến thể theo SKU) — đó là seam mà cart/pricing/inventory sẽ dùng.

Benefits: Locality: mọi luật BR-CAT-* ở một chỗ. Leverage: cart/pricing/inventory chỉ biết một interface nhỏ thay vì 3 module. Test: spec của Variant có thể test luôn ràng buộc Size/Màu thật, không mock module lân cận.

2. Gộp auth + staff thành module identity

Strong

Files: src/auth/**, src/staff/**, src/cli/create-admin.command.ts

Problem: Tài khoản nội bộ (InternalAccount) là khái niệm của identity, nhưng InternalAccountService nằm trong auth/services còn quản lý Staff nằm ở staff/, và staff + cli với thẳng vào ruột auth/services/internal-account.service.ts. Seam giữa auth và staff là giả: xoá ranh giới đó không làm phức tạp thêm gì (deletion test → nông). auth.service.ts 488 dòng vừa làm đăng ký, xác thực email, quên mật khẩu, phiên.

Solution: modules/identity/: storefront/ (auth, me), back-office/ (staff), service tách theo use case (registration, session, password-reset, internal-account). CLI create-admin gọi cùng service qua interface được exports.

Benefits: Mọi luật vòng đời Tài khoản (E5, US-1001, ADR 0005) có locality. auth.service.spec 823 dòng tách được theo use case, mỗi spec nhỏ và rõ.

3. Tách "cổng phân quyền" ra khỏi auth thành một decorator sâu ở common/

Strong

Files: auth/guards/{jwt-auth,roles,ownership}.guard.ts, auth/decorators/{roles,current-user,owned-resource}.decorator.ts, auth/decorators/is-strong-password.decorator.ts, config/env.validation.ts, mọi admin-*.controller.ts

Problem: Mỗi controller back-office lặp @ApiBearerAuth() @UseGuards(JwtAuthGuard, RolesGuard) @Roles(...) và import 3–4 file từ ruột auth/. Đây là lý do duy nhất catalog/staff phải imports: [AuthModule]. Quên RolesGuard ở một chỗ = lỗ hổng phân quyền im lặng; interface (3 decorator phải nhớ đúng thứ tự) gần phức tạp như implementation. Ngoài ra config import IsStrongPassword từ auth → hạ tầng phụ thuộc nghiệp vụ.

Solution: Một decorator @Authorize('STAFF','ADMIN') / @Public() (hoặc guard toàn cục + mặc định từ chối) sống ở common/auth/; JwtStrategy vẫn thuộc identity. IsStrongPassword chuyển về common/validation/.

Benefits: Leverage: một chỗ quyết định ADR 0005 (four-actor model) được áp ra sao. Test: một spec duy nhất cho decorator thay vì e2e mỗi controller phải kiểm "đã gắn đủ guard chưa". Module nghiệp vụ không còn cần import AuthModule.

Before (mỗi controller)
import { JwtAuthGuard } from '#src/auth/guards/jwt-auth.guard.js';
import { RolesGuard }   from '#src/auth/guards/roles.guard.js';
import { Roles }        from '#src/auth/decorators/roles.decorator.js';
@ApiBearerAuth()
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('STAFF','ADMIN')
After
import { Authorize } from '#src/common/auth/authorize.decorator.js';
@Authorize('STAFF','ADMIN')

4. Gom hạ tầng vào infrastructure/, xếp chỗ cho mail và audit

Worth exploring

Files: prisma/, health/, metrics/, mail/, audit/, bootstrap/, common/app-logger.ts, common/request-context.ts

Problem: Chủ yếu là vấn đề định vị: nhìn src/ không phân biệt được đâu là nghiệp vụ. mail theo docs thuộc notifications, audit thuộc admin-config — nhưng hai module này chưa có, nên tạo sớm cả module rỗng là YAGNI.

Solution: infrastructure/{database,observability(health+metrics+logging)}; tạm để mail, audit dưới infrastructure/ và chuyển về modules/notifications, modules/admin-config khi các module đó thực sự được làm.

Benefits: Thuần locality khi đọc code; không thay đổi interface, test không đổi. Rẻ nhưng lợi ích thấp hơn 1–3.

Top recommendation

Làm #3 (decorator phân quyền ở common) trước: nhỏ, cắt đứt lý do khiến mọi module nghiệp vụ dính vào ruột auth/, và sửa phụ thuộc đảo chiều config → auth. Sau đó #2 và #1 trở thành việc di chuyển gọn trong ranh giới mỗi module, làm trước khi bắt đầu pricing/cart/inventory — các module này đều phụ thuộc catalog, nên seam của catalog nên cố định trước khi có người dùng nó. #4 có thể đi kèm hoặc làm cuối.
