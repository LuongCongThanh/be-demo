Đúng. Sau khi xem lại v1.5, tôi đồng ý rằng **nên tách Admin và Storefront thành hai NestJS feature module riêng**, thay vì chỉ chia thành hai nhóm folder bên trong một `CategoryModule`.

Đây là một cải tiến đáng cân nhắc cho kiến trúc hiện tại, đặc biệt khi bạn muốn áp dụng cùng một convention cho Product, Product Option, Pricing và các module sau này.

Tuy nhiên, có một điểm quan trọng: **tách module xử lý không có nghĩa là nhân đôi toàn bộ Category Domain và Repository.**

## **1. Vấn đề của cấu trúc v1.5 hiện tại**

Trong v1.5, bạn đang có:

```
category/
├── application/
│   └── services/
│       ├── admin/
│       ├── shared/
│       └── storefront/
│
├── controllers/
│   ├── admin/
│   └── storefront/
│
├── dto/
│   ├── admin/
│   ├── shared/
│   └── storefront/
│
├── infrastructure/
├── domain/
└── category.module.ts
```

Cấu trúc này đã phân loại code theo Admin và Storefront, nhưng về NestJS, chúng vẫn được đăng ký trong cùng một module.

Điều đó có nghĩa là ranh giới giữa hai nhóm mới chủ yếu nằm ở folder, chưa được thể hiện rõ bằng module boundary.

Tôi nghĩ nên nâng cấp lên một cấp độ tổ chức khác:

- Admin có module, controller, use case và DTO riêng.
- Storefront có module, controller, use case và DTO riêng.
- Domain và các capability thực sự dùng chung vẫn được chia sẻ.
- Infrastructure dùng chung khi hai phía cần cùng persistence hoặc integration.

## **3. NestJS Module nên kết nối như thế nào?**

Tôi đề xuất ba cấp:

**CategoryModule**

Module tổng hợp feature Category

**AdminCategoryModule**

Admin controllers & use cases

**StorefrontCategoryModule**

Public controllers & use cases

**CategoryCoreModule**

Shared Port bindings và shared Application providers

**CategoryRelationalPersistenceModule**

Prisma Client và concrete persistence adapters

Cách hoạt động:

`CategoryCoreModule`

- Import Infrastructure module.
- Bind Application Port token sang concrete adapter.
- Export các Port token mà Admin và Storefront cần.
- Đăng ký shared Application provider nếu thực sự tồn tại.

`AdminCategoryModule`

- Import `CategoryCoreModule`.
- Đăng ký Admin Controller.
- Đăng ký Admin Application Service.
- Đăng ký Admin DTO và Presentation Mapper cần thiết.

`StorefrontCategoryModule`

- Import `CategoryCoreModule`.
- Đăng ký Storefront Controller.
- Đăng ký Storefront Application Service.
- Đăng ký Storefront DTO và Presentation Mapper cần thiết.

`CategoryModule`

```
@Module({
  imports: [
    AdminCategoryModule,
    StorefrontCategoryModule,
  ],
})
export class CategoryModule {}
```

Có một lưu ý quan trọng về NestJS: provider của một module không tự động được truyền xuống các module con hoặc module cùng cấp. Module muốn sử dụng provider cần import module cung cấp và provider đó phải được export. Nest cũng hỗ trợ chia sẻ instance của module/provider khi nhiều module cùng import một shared module. Vì vậy, Admin và Storefront cần import `CategoryCoreModule` trực tiếp, không chỉ dựa vào `CategoryModule` tổng hợp.&#x20;

## **4. Vì sao không nên tách Domain thành Admin và Storefront?**

Đây là điểm tôi muốn nhấn mạnh nhất.

Không nên làm như sau:

```
category/
├── admin/
│   ├── domain/
│   ├── application/
│   └── infrastructure/
│
└── storefront/
    ├── domain/
    ├── application/
    └── infrastructure/
```

Vì có thể dẫn đến:

- Hai Domain Model Category khác nhau dù cùng biểu diễn một nghiệp vụ.
- Hai Repository implementation cho cùng một nguồn dữ liệu.
- Business rule bị duplicate.
- Khi thay đổi Category tree hoặc slug, phải sửa nhiều nơi.
- Khó kiểm soát tính nhất quán giữa Admin và Storefront.

Thay vào đó, nên tách theo **application surface**, không phải tách đôi toàn bộ Domain.

Ví dụ:

| Nghiệp vụ             | Admin         | Storefront | Dùng chung                        |
| --------------------- | ------------- | ---------- | --------------------------------- |
| Create Category       | Có            | Không      | Domain rule                       |
| Update Category       | Có            | Không      | Domain rule                       |
| Delete Category       | Có            | Không      | Domain rule                       |
| Search Category       | Có            | Có         | Repository capability khi phù hợp |
| Get Category Tree     | Có            | Có         | Tree logic                        |
| Category Localization | Quản lý       | Truy vấn   | Locale rule                       |
| Category Image        | Upload/delete | Hiển thị   | Image domain rule                 |

Admin và Storefront có thể có Application Service khác nhau dù cùng sử dụng một Domain Model.

Một điểm khác cần giữ: Storefront không nên gọi `AdminCategoryService` chỉ để tái sử dụng logic. Nếu thực sự có logic Application cần dùng chung, hãy thiết kế capability dùng chung tại vị trí phù hợp. Nếu chỉ có business logic chung thì tái sử dụng Domain trực tiếp.

## **5. Áp dụng convention này cho các module sau**

Tôi đề xuất chuẩn hóa một template cho toàn bộ feature module:

```
<feature>/
│
├── domain/
├── application/
│   ├── ports/
│   └── shared/             # Chỉ khi có logic thực sự dùng chung
│
├── infrastructure/
│
├── admin/                  # Conditional
│   ├── admin-<feature>.module.ts
│   ├── application/
│   ├── controllers/
│   ├── dto/
│   └── presentation/
│
├── storefront/             # Conditional
│   ├── storefront-<feature>.module.ts
│   ├── application/
│   ├── controllers/
│   ├── dto/
│   └── presentation/
│
├── <feature>-core.module.ts
└── <feature>.module.ts
```

Không bắt buộc module nào cũng phải có cả Admin và Storefront.

Ví dụ:

| Feature                | Cách tổ chức có thể áp dụng                                 |
| ---------------------- | ----------------------------------------------------------- |
| Category               | Admin + Storefront                                          |
| Product                | Admin + Storefront                                          |
| Product Option         | Admin + Storefront nếu có cả hai luồng                      |
| Pricing                | Admin + Storefront nếu có chức năng quản lý và truy vấn giá |
| Internal Configuration | Chỉ Admin hoặc Internal                                     |
| Background Job         | Worker module riêng, không cần Controller                   |

Điều quan trọng là **mỗi feature surface có module riêng khi nó có boundary về use case, API contract, security hoặc lifecycle riêng**. Không tạo module chỉ vì muốn có thêm folder.

## **6. Có 3 quy tắc tôi muốn đưa vào convention mới**

| Quy tắc                                                                                                                               | Mức độ |
| ------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| Admin và Storefront phải có module riêng khi có hai nhóm use case/API độc lập đáng kể.                                                | SHOULD |
| Không để Storefront phụ thuộc trực tiếp vào Admin Application Service, và ngược lại.                                                  | MUST   |
| Domain, shared Port và Infrastructure chỉ được dùng chung khi cùng thuộc một nghiệp vụ/capability; không nhân đôi chỉ để tách module. | MUST   |

Tôi cũng đề xuất thống nhất tên `storefront/` thay vì `store/`, vì `store` có thể bị hiểu là nghiệp vụ cửa hàng hoặc chi nhánh bán lẻ, còn `storefront` thể hiện rõ public-facing application surface.

## **Kết luận**

Tôi khuyến nghị thay đổi v1.5 theo hướng này.

Nó giúp kiến trúc phân chia thành ba loại ranh giới rõ ràng:

1. **Domain boundary:** Category, Product, Pricing...
2. **Application surface boundary:** Admin, Storefront, Internal/Worker khi cần.
3. **Infrastructure boundary:** Database, Storage, External API...

Như vậy, mỗi module có thể phát triển độc lập ở phần xử lý Admin và Storefront mà không nhân đôi nghiệp vụ cốt lõi.
