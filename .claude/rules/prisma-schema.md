# Prisma schema and client — agent-condensed (full conventions: docs/convention/prisma-conventions.md; target schema: docs/architecture/11-database.md)

This condensed guide lists rules for agents creating or editing schemas and Prisma Client calls. Check `11-database.md` for specific tables, columns, and indexes.

## Schema conventions

- Multi-file schemas (`prisma/schema/*.prisma`) are merged automatically by Prisma; no imports are needed. Declare enums in `prisma/schema/enums.prisma`.
- Naming: use singular `PascalCase` model names and map plural `snake_case` table names with `@@map("...")`. Use `camelCase` for code fields and map `snake_case` database columns with `@map("...")`.
- **Money uses `BigInt` (integer VND)**—not `Float` or `Decimal`. Add `CHECK >= 0` constraints in SQL migrations.
- Use `@db.Timestamptz(6)` for timestamps. Use `id String @id @db.Uuid` for primary keys (UUID v7 generated by the app), except lookup tables with natural keys and join tables.
- Declare each foreign key as a pair: the actual FK column (`xId String @map("x_id") @db.Uuid`) and its relation field (`x X @relation(fields: [xId], references: [id])`).
- Always declare `onDelete` explicitly; do not rely on defaults. Follow section 3.3 of `11-database.md`: use `Cascade` for dependent records (`cart_items`, `refresh_tokens`) and `Restrict` for financial/history records and category trees. Every FK must have an index.
- For pure many-to-many join tables, use a composite PK (`@@id([a, b])`) at the end of the model; no separate `id` column is needed.
- Add `@@index([...])` for frequently filtered/sorted queries. Index field order must match `where`/`orderBy` usage so Postgres can use an Index Scan instead of a Seq Scan (verify with `EXPLAIN ANALYZE`).
- **Partial unique indexes (`UNIQUE ... WHERE ...`) cannot be expressed in Prisma DSL.** Run `prisma migrate dev --create-only`, add `CREATE UNIQUE INDEX ... WHERE ...` to the SQL migration manually, then apply it with `prisma migrate dev`.
- Pass `--config prisma7.config.ts` to every Prisma command (the project does not use the default `prisma.config.ts` name). Prisma v7 `migrate dev` does **not** run `generate` or seed automatically; invoke them separately when needed.

## Prisma Client trong NestJS

- Use one module per domain and inject the shared global `PrismaService`. Do not create a separate `PrismaService`; a Repository layer is unnecessary at the project's current scale. In modules covered by [module architecture](module-architecture.md) (new modules and migrated modules), follow that rule instead. There, only Prisma adapters in `infrastructure/` use `PrismaService`, and transactions use the `TransactionRunner` port.
- For atomic business operations (for example, checkout), use an interactive `prisma.$transaction(async (tx) => {...})`; every query in it must use `tx.`, not `this.prisma.`. Errors inside the transaction roll back all changes.
- Update quantities with atomic operators (for example, `{ decrement: n }`) instead of manual read-then-write logic to avoid race conditions.
- Avoid N+1 queries: use `include`/`select` to fetch related data in one query instead of looping over database calls. Temporarily enable `log: ['query']` to investigate suspected N+1 queries.
- Pagination: use offset pagination (`skip`/`take`) for small admin dashboards and cursor pagination (`cursor: { id }` plus `skip: 1`) for large public listings, matching an existing `@@index`.
- For race conditions, prefer row locks (`SELECT ... FOR UPDATE` via `$queryRaw` in `tx`) or conditional updates, following `docs/architecture/04-data-consistency.md`. Consider `{ isolationLevel: 'Serializable' }` with retry logic only when encountering `P2034`; do not apply it broadly because it is slower than the default `Read Committed`.
- When changing a schema with real data, add a required column with `@default(...)` or make it nullable first. Rename a field with `@map` to preserve the old column, or explicitly rename it in SQL. For changes that could lose data, run `migrate dev --create-only` and inspect the SQL before applying it.
- Use `migrate dev` only on development machines and `migrate deploy` in production/CI (it does not create migrations). Rollbacks are not automatic; create a new migration that reverses the change.
